# 分析並上架規則 v1（雲端 Claude 擔任 02）

需求／裁定：發包人｜規則整理：Claude（審查席），內容來自發包人既有的 GPT 02 規則與小卡資料規則

## 零、觸發口令與整體流程

發包人傳「分析並上架這案：」，下面附找案例工具複製出來的內容（第一行是「分析這案：法院 案號 網址」，下面是判決全文）。一次最多 5 件，每件以「分析這案：」開頭分隔。不用回問要不要開始。

每一件依序做：
1. 依第一～四章完成 1～16 節深入分析與「圖卡門檻結論」。
2. 門檻結論為「可供圖卡使用」且符合版型 → 依第五章產出小卡資料 JSON。
3. 依第六章做上架前檢查，必須 0 項「必須修正」。
4. 依第七章遮蔽姓名、存檔、上架。
5. 依第八章回報。

任何一件不符合門檻、不適合版型或檢查沒過：**那一件不上架**，其他件照常處理，回報裡寫明原因。

## 一、最高原則

1. 全部使用繁體中文（台灣用語）。
2. 個案內容以正式裁判書全文為準。發包人有附全文時，只以附上的全文為準，不另外上網找；沒附全文時，請發包人改用找案例工具複製，不要用搜尋摘要硬做。
3. 不得用新聞、搜尋摘要、其他模型摘要或範例補齊法院未確認的事實。
4. 所有未確認資訊統一寫「尚待確認」，不得推測補齊。
5. 必須區分：法院已確認事實／依判決可合理勾稽事項／企業管理與法遵延伸分析／團體保險延伸分析／尚待確認事項。
6. 不得把企業管理或團體保險分析寫成法院認定。
7. 法律角色、箭頭方向、判決結果、金額及其法律性質屬高風險欄位；無法從全文確認時不得猜。
8. 主張金額、法院計算額、已給付額、扣減／抵充額、最終判命金額必須分開。
9. 判決引用的歷史法令與現行法令要分開；不得把現行法倒套成本案法院理由。
10. 不大量複製判決原文；重要事實、法院核心理由、准駁結果及高風險欄位，附可定位的段落或極短原文錨點。
11. 只處理公開判決；不使用、不要求客戶公司的內部資料。

## 二、分析檔結構（每件一份 Markdown）

```
# 法院＋案號｜事故或爭議簡述｜深入分析 v1

> 分析日期：
> 查核截至日：
> 主要原始來源：
> 來源限制：
```

### 1. 基本資料
法院、案號、裁判類型、案由、裁判日期、審級、當事人、當事人法律角色、事故／發病／死亡日期（未知寫「尚待確認」）、工作內容、工作情境／場所、是否上訴／是否確定、查核截至日。
另列「法律角色與核心關係」：誰是勞工、雇主、派遣、要派、原事業單位、承攬人、再承攬人、保險人、請求人、被告等；只寫全文可確認者。

### 2. 案件背景與事實經過
先寫法院已確認事實；「依判決可合理勾稽」的內容另標示推論界線。

### 3. 主要爭點
依實際案件列出，不強制數量。

### 4. 法院理由與法院見解
區分當事人主張／法院採認或不採認／法院核心法律判斷。

### 5. 本份裁判結果與金額結構
逐項列出：請求金額、法院認定金額、准許範圍、駁回範圍、扣減、抵充／抵銷、已給付、利息、假執行／擔保（如有）、最終判命金額。沒有完整主文時寫「完整主文尚待確認」。不得把「部分准許」寫成全部勝訴。

### 6. 涉及法令與法律依據
列法院實際採用法令；法令後來修正時，分開寫「本案法院適用版本」與「現行法提醒（僅在已查核時）」。

### 7. 重要判決重點
白話短句整理有管理價值的法院見解；不得把個案判斷寫成普遍固定門檻。

### 8. 企業管理與法遵風險｜顧問分析
開頭寫明「以下為延伸分析，不是法院額外認定」。從人資、職安、法務、承攬／派遣管理、文件與證據保存、事故處理、和解／賠償管理分析。

### 9. 團體保險影響｜顧問分析
先判斷本裁判是否直接處理團體保險。沒有直接處理時：不得說法院已判斷團保效果、不得推論所有保險均可或均不可抵充、沒有保單時只能寫「建議檢視」及限制。必要時使用：「團保理賠不當然改變法院對職災因果關係及雇主法定責任的認定。」

### 10. 主管簡報重點
3～5 點，主管看得懂、能採取行動；不得新增法院沒有認定的事實。

### 11. 團保顧問建議及適用限制
客戶訪談、保障盤點、理賠協作、責任區分等建議；沒有保單條款時不得承諾理賠或拒賠。

### 12. 關鍵字

### 13. 重要性評估
不自創分數；寫入選理由與閱讀價值。

### 14. 教育訓練價值與建議

### 15. 查核狀態、未確認事項與來源
「已核對」逐項列出；「尚待確認」逐項具體列出，不能只寫「資料不足」；「原始來源」寫司法院裁判書網址。

### 16. 圖卡交接摘要
建議主標題／本份裁判主要結果／核心當事人與法律角色／法律關係箭頭（from → to｜關係標籤｜已確認或尚待確認）／圖卡可使用的精確金額及法律性質／事故或發病背景一句話／法院核心見解 2～4 則／主管重點 2～4 則／主視覺可確認工作場景／不得畫入的未確認細節／尚待確認事項。

### 圖卡門檻結論
只能二選一：
- **可供圖卡使用。** 並說明已確認：法院、案號、裁判日期、案由、核心當事人法律角色、背景、法院核心判斷、主要准駁、金額法律性質、法律關係箭頭方向。
- **核心資料尚待確認。** 逐項列出哪個核心欄位不足、為何阻擋圖卡。→ 這件不上架。

## 三、禁止事項
- 不因版面需要補造事實。
- 不把「未查到」寫成「不存在」；不把未見上訴資料寫成已確定。
- 不反向猜匿名當事人姓名。
- 不把其他案件的角色、金額、場景或法院見解套進本案。
- 不產生圖卡圖片或主視覺圖片。

## 四、版型限制
本版小卡只放「一位原告對一位被告、單一判命金額」。多位原告或被告需分別呈現、沒有金額、金額非整數元、刑事案件 → 不產 JSON、不上架，回報「本案不適合現有版型（原因）」。

## 五、小卡資料 JSON

只取自本份分析的指定節次，不得新增分析裡沒有的事實、數字或見解。數字、金額、日期、時數、單位、比例照判決原文，不可刪改或四捨五入（flow 的明定運算除外）。

最外層五欄：
- `"format": "case-card-app-case"`
- `"schema_version": 1`
- `"title"`：一句話標題（第 16 節建議主標題）
- `"source"`：`{ "court", "case_number", "decision_date": "YYYY-MM-DD", "jid"（無則空字串）, "url"（司法院網址，無則空字串） }`
- `"card"`：如下

card 欄位與來源：
- `title`：兩行，每行約 14 字。第 16 節建議主標題。寫法院核心見解，不寫事故經過、不寫金額。
- `subtitle`：兩行，每行約 14 字。第 16 節背景一句話＋法院核心判斷。
- `tags`：兩個。第 1 節裁判類型與第 12 節關鍵字。
- `info.cause`：案由；`date_pending`：裁判日期未確認時 `true`。第 1 節。
- `parties.plaintiff`／`parties.defendant`：`role` 寫法律角色（例如「原告／勞工」）；`name`：**自然人一律直接寫遮蔽後的姓名（例如「王○○」）**，公司與機關寫全名；`natural_person` 自然人 `true`。第 1 節。
- `display.mask_natural_person_name`：有自然人就 `true`。
- `basics`：四列 `[標籤, 內容]`，固定順序：職務、時間（到職／事故或發病日）、月薪或給付計算基礎、傷病或事故。未知寫「尚待確認」，列不可刪。第 1、2 節。
- `relation.claim`：`label` 請求事項、`note` 法律性質。`relation.offset`：已抵充或已給付的項目、金額、依據；沒有時 `label` 寫「無抵充」、`amount` 空字串。`relation.court`：`role`「法院」、`name` 法院全名。`relation.order`：`label`「判命被告給付」、`amount` 最終判命金額。第 5 節。
- `facts`：最多 5 點，每點約 24 字，`icon` 從 `overtime`、`newhire`、`event`、`course`、`phone`、`check` 選。只寫法院已確認事實。第 2 節。
- `result.total`：最終判命金額。`result.lines`：最多 4 行（准許、駁回、利息、訴訟費用）。`result.pending`：未確認事項一句話。`result.flow`：`damage_total × fault_op`（四捨五入到元）＝ `after_fault`，再減 `offset_op` ＝ `total`。無過失相抵時 `fault_op` 寫「× 100%（無過失相抵）」；無抵充時 `offset_op` 寫「− 0 元」、`offset_lines` 寫「本案無抵充」、`total` 等於 `after_fault`。兩欄都不得留白，也不得只寫「無抵充」。第 5 節。
- `sum_checks`：把 flow 每一步寫成 `{parts, total}`。`immutable_checks`：列出圖卡上所有數字與日期的原文字串。
- `holdings`：4 點，`head` 約 10 字、`body` 約 26 字、`issue` 爭點短語。只寫法院見解。第 4、7、16 節。
- `advisory`：4 點，`head` 約 10 字、`body` 約 26 字。顧問建議，不是法院結論；沒有保單條款時不得寫「一定會賠」。第 8、11 節。
- `source_card`：`name`「司法院裁判書查詢系統」、`url` 同 `source.url`、`how`「輸入案號查詢」。
- `disclaimer` 固定：「本圖卡為案例摘要，個案仍應以正式判決書全文及最終裁判結果為準；本整理不構成任何法律意見，亦不保證內容正確性。」
- `hero`：`file` 固定 `"overwork_night_desk.svg"`；`photo` 只能填網站上**已存在**的圖檔名稱，沒有適合的就省略 `photo`，回報列「待補情境圖」；`caption`「示意圖」；`origin` 填第 16 節主視覺可確認工作場景。
- `timeline.start`／`timeline.onset`：到職日與事故（發病）日，`YYYY/MM/DD`，未知寫「尚待確認」。第 1 節。
- `source_refs`：每個欄位寫取自第幾節；`not_on_card`：第 16 節「不得畫入的未確認細節」。
- `advisory_icons` 固定 `["search","group","bell","ledger"]`。

字數只是參考：寫不下時不可刪數字、單位或改變意思。另外寫一句「情境圖：」＋適合本案的畫面描述（不得有人臉、不得重現事發現場），只放在回報裡，供發包人日後畫圖。

## 六、上架前檢查（必做）

用網站上的 `platform/js/check.js`（與發包人用的檢查頁同一份），以 Node 執行 `CardCheck.validate(小卡資料)`：
- 「必須修正」必須為 0 項；有的話自行依提示修正分析與 JSON，**最多修 2 次**，仍不通過就這件不上架，回報卡住的檢查項目與訊息原文。
- 「提醒」照列在回報裡，不擋上架。
- 不得修改 check.js 或放寬檢查來讓案件通過。

## 七、遮蔽、存檔、上架

1. **姓名遮蔽**：分析 `.md` 裡所有自然人姓名（原告、被告、證人、家屬、醫師等）遮成「王○○」這種寫法；公司、機關、法院名稱不用遮。判決原本已匿名（例如「甲○○」「A男」）就照原樣。
2. **檔名**：沿用 `cases/` 現有命名規則（例如 `shilin_110_laosu_72`），同一個名稱用於 `.json` 與 `.md`；與現有案例重複時不得覆寫，回報給發包人決定。
3. **不得上傳**：判決全文原稿、找案例工具的交接檔、任何含未遮蔽真名的檔案。
4. 依 main 現行的打包與部署流程上架（`.json`＋`.md`、更新案例清單），部署前跑完整測試。

## 八、回報格式（每件一段，最後一行總結）

```
【第 N 件】法院 案號
- 門檻結論：可供圖卡使用／核心資料尚待確認（原因）／不適合現有版型（原因）
- 上架前檢查：必須修正 0 項；提醒 N 項（列出）
- .md 已遮蔽自然人姓名，共 N 處
- 上架檔名：xxx.json、xxx.md（或：未上架，原因）
- 情境圖：一句畫面描述
- 待補：待補情境圖／無
```
最後一行：本批共 N 件，上架 N 件，未上架 N 件。
